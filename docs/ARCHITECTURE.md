# Sangitam architecture

Sangitam keeps a small, explainable separation between the Swing interface and the work behind it. The working journey is **choose a file or folder → scan metadata and audio → save tags → build an editable session → play**.

## How the pieces connect

```text
SangitamApp
  └─ MainFrame (navigation and shared state wiring)
       ├─ Swing panels: Dashboard, Search, Discover, Library, Import dialog, Player bar
       ├─ DiscoverPanel → MusicProvider adapters → official catalog APIs
       ├─ LibraryService
       │    ├─ LibraryScanner → Track
       │    ├─ AudioAnalyzer → TrackTags
       │    └─ LibraryStore → local SQLite file
       ├─ SearchPanel → LibrarySearchStore → bounded pages from the same SQLite file
       ├─ SessionPlanner → chosen tracks with reasons
       └─ PlayerService → VlcjPlayerService → libVLC (JavaFX Media fallback)
```

`MainFrame` owns one `LibraryService` and one `PlayerService`. Dashboard and Library receive catalog snapshots; Search receives renderer state and queries its result pages through `LibrarySearchStore`. Panels do not contain sample collections or SQL. A double-click or Enter on a song sends a `Track` to `MainFrame`, which asks the player to open it; group results open the collection page. The player sends an immutable `PlaybackState` to the Swing player bar.

`PlayerBar` delegates every action to MainFrame, including linked title/cover navigation, role-ordered artist links, liking through existing song pins, EQ, spectrum, and the queue/history dock. `MarqueeButton` scrolls only overflowing titles while attached to a component hierarchy. `RoundSliderUI` paints rounded rails and supports click/drag seek with one commit on release. Artwork runs through the existing versioned background cache. The vertical library rail hosts `QueueHistoryPanel` in its lower half; expanding the library hides the dock and still calculates expansion against workspace width.

`ArtistCredits` provides exact normalized identities and display priority (composer, conductor, soloist, performers, orchestra, album artist, remaining artist). It preserves commas and splits explicit semicolon/spaced-slash lists. `ArtistPageData` builds local top-ten, liked/pinned songs, complete matching local album groups, and bounded shared-credit collaborators off the EDT. `ArtistPanel` loads user profiles and portraits in workers and rejects obsolete loads. `ArtistStore` adds offline profile BLOBs and descriptions, per-path elapsed listening, and persistent artist-credit mappings. These records survive library removal; file audio and provider credentials are never stored in profiles. Portrait decoding is bounded and resized to a 320-pixel local image. The online-catalog entry point only prefills Discover; it does not fetch automatically.

`ListeningClock` uses monotonic wall time while a decoder reports Playing. Seeks do not add duration; pauses do not accumulate time, and a long stall contributes at most two seconds per observation. MainFrame batches deltas every ten seconds through `PlaybackMemoryService`. Opening an artist flushes queued deltas before loading totals using a serial-worker barrier. No duration is inferred from legacy play counts. SQLite listening-credit mappings preserve attribution when a library row is removed and update from current credits on future listening. The normal close path disposes the window instead of calling System.exit, allowing the existing non-daemon memory worker to finish final writes.

`Track` is an immutable record containing a normalized file path, title, artist, album, duration, format, genre, and optional `TrackMetadata`. The path is the database key, so importing the same file again updates one row rather than creating a duplicate. Metadata contains separate classical roles with origins, custom tags, technical header properties, embedded-artwork presence, and an extraction version. The scanner recognizes MP3, WAV, FLAC, OGG/OGA, AAC, M4A, AIFF, and WMA by extension, reads embedded metadata with Jaudiotagger, and falls back to the filename when labels are empty. `ClassicalHints` supplies only conservative explicit-text hints; `TagVocabulary` supplies user suggestions, not audio predictions. The scanner does not follow directory symlinks. The file browser enumerates drive roots, reads the remembered location, and builds directory listings on Swing workers.

Imports remember the selected canonical paths and recursion settings in `library_sources`. A rescan walks those sources and checks previously indexed paths outside the current source results. The scanner reuses metadata when file size and modification time match the saved stamp. Analysis uses its own freshness stamp. Import and rescan workers serialize with each other and release the store monitor during filesystem traversal and audio analysis. Each scan commits metadata, source settings, availability, and new analysis results together, then publishes an immutable catalog snapshot to Swing.

Availability is stored on the track row and reflects the most recent check. An unavailable row retains its path, tags, playlists, and listening history. Search and the library render that state from the catalog snapshot without checking the filesystem. A successful scan of the original path clears it. Older databases start with unknown metadata stamps and an empty source list. Rescan checks their indexed files, and explicit folder imports register new discovery scopes.

The scanner can bypass the metadata stamp for placeholder labels or an outdated metadata extraction version. Startup schedules the refresh using the same scan worker and transactional upsert as rescan. It leaves the source list and file tags alone. The folder tree is built from indexed paths on a Swing worker and attached on the event thread. Expansion and selection are restored by path when metadata changes.

General now separates its complete mixed-entry snapshot from its displayed page. `GeneralLibraryPages` filters/sorts immutable entries and organization state on a worker, preserves pins and deterministic ties, and returns at most 100 rows plus total/offset. `LibraryPanel` invalidates pending pages immediately on text changes, resets offset for query/order/scope changes, preserves/clamps offset for catalog refresh, and rejects obsolete worker generations. Off-page entry lookup and complete group membership remain available to existing context actions, drag/drop, and collection pages. This is snapshot-backed presentation paging; the full mixed snapshot is still built in memory.

Locations uses `LocationIndex`, an immutable map of indexed folder children and direct track lists with common roots per filesystem root. It performs no filesystem or media I/O. Filtering, sorting, and locating a restored selection's branch page happen on workers. `LibraryFolderTree` creates Swing nodes only for expanded branches, with at most 100 data children and two navigation rows per branch page. Changing page replaces that branch's children; collapse cancels its jobs and releases loaded descendants. Generation and worker-identity checks reject stale indexes/child pages. Reindexing restores visible expansion and selects the page toward a saved path, while failed work presents a retry row. The full path/track index remains resident, and total expanded branches can still consume memory; there is no fixed global node cap or database-backed branch query yet.

General library rows combine catalog snapshots with the virtual organization snapshot. `CollectionStore` stores virtual folder parents, direct song membership, scoped playlist names, and pins in the existing SQLite database. The playlist migration preserves IDs and item positions. Collection mutations are serialized with the store, and folder moves reject descendants as destinations. Track identity remains the indexed path. Album rows group by album name and credited artist. The Liked Songs projection uses persisted song pin keys. Regular and smart playlists retain their existing storage. Queue actions share MainFrame’s existing ordered playback session. Cover reads run through a bounded background cache and use embedded local artwork.

Home uses `LibraryDashboardStore.recent` to read at most 12 available tracks ordered by recorded `last_played_at` and path, backed by an index. `HomeLibraryData` resolves at most eight pinned playlists (including smart lists) from the immutable catalog on the collection worker. Only shelf entries and their first three cover-candidate stamps reach `HomeLibraryPanel`. The shelf lists reuse library context menus and collection navigation; updates do not replace the active playback queue. Collection revisions reject late older results, and a worker overtaken by a catalog publication refreshes against the newer snapshot. Other dashboard/session features still depend on the full loaded catalog.

`LibraryArtwork` owns a single background worker, at most 24 pending requests, and an LRU cache of 160 decoded/negative results per instance. Cache keys include the indexed file size and modification time, so rescanning a changed file invalidates its previous cover, including an earlier missing-cover result. An old read cannot overwrite the newer version. General uses 42-pixel art; Home uses 72-pixel art. Covers are sampled while decoding, with an 8 MB compressed-data limit and 12,000-pixel dimension limit. Closing clears the cache and suppresses late repaint callbacks. External image references and changes that preserve both file size and timestamp are not detected.

`DetailReset` describes explicit fields to follow from the file again. `LibraryService.restoreDetails` serializes with scans, forces a fresh metadata read for selected indexed paths, and passes only successful reads to one `LibraryStore` transaction. Basic override flags are cleared only for selected labels; `MetadataStore` releases selected credit/tag overrides and rebuilds searchable text. Unreadable or removed rows retain their corrections, and a database error rolls back the whole successful-read batch. A partial reset deliberately preserves the previous metadata stamp/extraction version so it cannot hide a later full refresh of unselected automatic values. No source registration, exclusion, audio-file write, or mood reanalysis is involved.

`Playlist` now carries an optional immutable `SmartPlaylistRule`. Regular playlists retain their ordered `playlist_items`; smart playlists store versioned rule JSON in `smart_playlist_rules` and resolve a bounded path snapshot during `LibraryStore.loadPlaylists`. `CollectionStore` saves identity/rule edits in one transaction, and a delete trigger cleans rules when a playlist or its containing folder is deleted. The UI and storage layer reject manual appends to smart targets; copying the current matches to a regular playlist materializes a fixed list. Existing playlist constructors and IDs remain compatible.

`SmartPlaylistStore` shares one evaluator between preview and resolution. All enabled conditions are ANDed, values are bound, text wildcards are escaped, and ordering has deterministic path ties. Exact genre/tag comparisons use a per-connection Java case-fold function, including Unicode labels. Rating filters require current automatic or explicit manual ratings. A preview counts matches and loads at most 20 examples in one read snapshot; saved resolution loads at most the rule's limit (1–5,000). SQLite progress handlers check cancellation. `SmartPlaylistPanel` runs preview on a worker, rejects late generations, commits typed numeric edits before validation, and closes its worker with the dialog.

Catalog updates request another background collection load in `MainFrame`, so imports, edits, availability changes, and recorded plays update rules. Existing collection revision guards reject older loads. An already started queue keeps its captured order; it is not automatically replaced by new rule matches.

Catalog detail edits preserve separate overrides for title, artist, album, genre, and analysis ratings. Rescan upserts honor those overrides. Library removal records a path exclusion and removes catalog rows in one transaction. Playlist and listen references keep their paths so an explicit reimport can restore the catalog entry.

`MetadataStore` shares the scan/detail transaction and keeps an optional JSON payload per path in `track_metadata`. It merges fresh file data with per-field user overrides and an independent custom-tag override. An explicit empty value remains an override, preserving a user's clearing. Technical properties always refresh from the scan. The same transaction rebuilds normalized search text from the merged labels and metadata. An AFTER DELETE trigger cleans up metadata when a catalog row is removed. Existing catalog, playlist, and history schemas remain compatible. `TrackDetailsPanel` builds a patch from explicit edits; it performs no persistence itself.

`AudioAnalyzer` decodes bounded PCM through Java Sound and MP3SPI and calculates energy and activity. `SpectralFeatures` computes a continuous envelope, tempo evidence, spectral centroid, and chroma evidence, then derives a heuristic arousal/valence palette. `AudioFeatureStore` persists a versioned payload keyed by track path and file stamp. Legacy energy/activity overrides survive independent feature refreshes. The analysis worker is cancellable and publishes coverage while processing large libraries.

`SessionPlanner` scores playable candidates against the requested energy arc, mood, intent, metadata, familiarity, diversity, and taste. `TasteStore` records explicit preferences and timestamped playback windows alongside artist listening totals. `SessionContext` uses fresh contiguous listening first, then weights the device’s history by similar local time and date. A worker builds a draft from a catalog snapshot, and a generation guard prevents stale requests from replacing it. `SessionQueuePanel` presents the energy contour, selection reasons, replacements and editing. `MainFrame` routes transport through the active queue and keeps an edited draft separate when a session is already playing.

SQLite is confined to the storage package. `LibraryStore` owns connections, catalog transactions, and schema initialization; `CollectionStore`, `MetadataStore`, `LibrarySearchStore`, and `SmartPlaylistStore` implement focused storage concerns. `AppPaths` locates the database in the user's application-data area. `TrackSearch` remains a pure helper for loaded-track filtering. The Search screen uses `LibrarySearchStore` instead: it reads counts and pages in one transaction, binds and escapes literal queries, sorts with stable ties, and checks interruption through SQLite's progress handler. Each category loads at most 100 rows in the UI (API maximum 250). General, Locations, dashboards, session planning, and catalog snapshots still load the catalog in memory. Leading-wildcard substring queries can scan all rows; this is not an FTS index.

`DiscoverPanel` is a separate search path for online catalogs. Each `MusicProvider` adapter reads only catalog metadata and constructs a link on the provider's official domain. MusicBrainz works without a credential. The other adapters use the provider credential service, which supports Windows Credential Manager and environment variables for development. A `CatalogTrack` is intentionally distinct from the local `Track`, so online results cannot accidentally enter local playback or the tag-based session queue.

Artist enrichment is separate from catalog discovery. `ArtistEnrichmentClient` requests Wikipedia extracts and eligible Commons thumbnails on a worker. `ArtistEnrichmentStore` caches profile data and source credits and applies aliases in a SQLite transaction. It updates affected indexed credits, search text, pins, and listening credits. The artist page gives user profile edits priority over the online cache. [Artist enrichment and mood sessions](ARTIST_ENRICHMENT_AND_MOOD_SESSIONS.md) traces these paths.

`ListeningInsightsStore` reads measured playback totals and groups them by current catalog genre, classical period, and fresh audio mood estimate. Removed tracks keep their seconds in a separate bucket. It groups saved listen events by source in the same read transaction. `ListeningInsightsPanel` loads this snapshot on a cancellable worker when its Rediscover tab is selected or refreshed. Provider event counts and local elapsed time are presented as separate measures.

## Threading

The Windows app image uses the native jpackage GUI launcher with a bundled runtime and shared icon source. `SangitamApp` creates the shell on Swing, and its first paint schedules workspace construction. Online views load on demand, the decoder is created on playback demand, and optional credential and media-key initialization follows first paint. The optional startup trace separates process start, paint, workspace, catalog and first library page. [Windows launcher and scale test](WINDOWS_LAUNCH_AND_SCALE_TEST.md).

The collection executor serializes edits and coalesces passive refreshes. Catalog snapshots carry a path index and measured-track count, which avoid full scans for selection and coverage on Swing. Play history changes reuse the catalog metadata while updating counts and recency. General reuses sorted snapshot lists and builds at most one page plus a fallback page per request. Startup analysis skips probes for tracks with current indexed measurements.

Swing components are created and updated on the Event Dispatch Thread. `LibraryService` uses `SwingWorker` for initial database loading, folder scanning, audio analysis and database writes; it publishes progress and final catalog snapshots back on the Event Dispatch Thread. Old libraries are analyzed after their track list is already visible. Session building and file-existence checks run in another worker. Search filtering runs in a debounced `SwingWorker`. Online HTTP searches and browser launches also run in `SwingWorker`s with timeouts. Library and soundscape animations use `javax.swing.Timer`.

`PlayerService` remains the transport boundary. `VlcjPlayerService` uses one command executor to serialize libVLC calls and sample the active player's status, position, and seekability. It reuses the libVLC factory and creates a new media player for each open. End and error callbacks return to the command executor and are scoped to that media player. It prepares libVLC after the first UI paint and falls back to `JavaFxPlayerService` when native initialization fails. JavaFX commands and callbacks run on the JavaFX application thread. Both adapters discard obsolete playback snapshots when a newer track is requested and deliver current snapshots to Swing. The position bar previews during a drag and sends one seek on release. The decoder supplies the duration and reconciles the result. VLC is an external dependency. The Windows media-key listener uses JNativeHook as a transport fallback; it ignores those keys while SMTC is active, and leaves hardware volume keys to Windows to avoid applying two gain changes.

`WindowsMediaBridge` asynchronously starts the optional compiled .NET companion in `bin/native`. `MediaHost.cs` owns an invisible window and gets SMTC through the documented desktop interop factory. Its pipes carry bounded latest-state updates, Base64 UTF-8 metadata, and a small validated command vocabulary. Commands return on Swing's EDT to the same MainFrame methods as buttons; app state publishes status, timeline, shuffle, and repeat back to SMTC. Pipe failure restores the hook fallback. EQ, artist navigation, and app gain are app controls; Windows system volume is separate. The helper requires Windows metadata/.NET Framework and is compiled by `native/build-media-host.ps1` during the Windows build. Its protocol-check mode exits before creating any window/session. Runtime registration and Windows interaction still need manual verification.

Provider API secrets are read from Windows Credential Manager on a background worker and cached in memory for the session. The Settings dialog writes credentials through a small Windows Credential Manager bridge. Environment variables remain a development fallback. The custom Swing file browser stores only its last directory in Java Preferences.

`AudioSettings` holds the EQ curve, manual preamp, and ReplayGain selection. `LiveAudioPreview` immediately sends the first edit, then coalesces continuous Swing slider changes at 30 ms intervals without waiting for release. Cancel drops pending edits before restoring saved settings. The adapters change the active equalizer on their existing decoder threads; JavaFX retains its bands during adjustment. EQ does not reserve automatic headroom. VLC 3's single-pass filter multiplies its dry path by 0.25, so the VLC adapter offsets its native preamp by `20*log10(4)` to make the application's 0 dB setting unity gain. The native options explicitly disable two-pass EQ.

`PlayerService.setVolume` accepts VLC-style percentage ratios from 0 to 1.5. VLC receives 0–150 directly; JavaFX applies the equivalent cubic curve and advertises its 100% ceiling. The UI and shortcuts follow that ceiling. ReplayGain is VLC-only, uses embedded tags with peak protection and zero default gain, and is committed on Save rather than preview. A changed mode recreates the libVLC factory between tracks, since these audio options belong to the instance. `AudioSettingsStore` loads and atomically replaces non-secret `audio.properties` on Swing workers; it uses the library's data directory and does not alter SQLite or media files.

`CoalescedCommand` prevents rapid volume edits from accumulating redundant decoder jobs: a queued operation reads the latest requested value, with no UI debounce before the first submission. Volume persists separately in SQLite app_state through the memory worker; a short write debounce does not delay the audio command. `AudioSettingsDialog` is only a modal shell around headlessly testable `AudioSettingsPanel`; bands/preamp remain enabled while bypassed and edits automatically activate EQ. ReplayGain help is a tooltip. JavaFX's spectrum listener returns copied, track-scoped real magnitude arrays to Swing only while requested; VLC currently reports spectrum unsupported. `SpectrumPanel` renders data or an explicit unavailable/paused state.

`ShortcutBindings` validates and normalizes 16 app-local commands, disallows reserved editing/navigation keys, and rejects duplicate active bindings. `ShortcutStore` saves versioned JSON in app_state. `ShortcutPanel` captures keys without parsing user-typed Swing syntax. MainFrame replaces previous root bindings only after a successful save and updates menu accelerators. Plain Space does not trigger an app command from a text component. Hardware media controls remain a separate bridge. Unimplemented menus are disabled and have no accelerators; sorting, player visibility, recent history, and shortcut menus perform real actions.

## Presenting the code

1. Start at `SangitamApp`: install the theme and create `MainFrame` on the Event Dispatch Thread.
2. Show `MainFrame`: one place wires screens, the library and the player together.
3. Import a test folder: `ImportMediaDialog` passes paths to `LibraryService`; `LibraryScanner` reads metadata; `AudioAnalyzer` measures sound; `LibraryStore` saves both.
4. Search: `SearchPanel` submits a bounded `LibrarySearchStore.Request` on a worker and uses a generation number to reject late results.
5. Play a track: a panel sends `Track` to `MainFrame`, then `PlayerService` reports a `PlaybackState` to `PlayerBar`.
6. Build a session: `SessionPlanner` chooses tracks with reasons; edit the Swing queue, start playback, then show how next and previous follow its order.
